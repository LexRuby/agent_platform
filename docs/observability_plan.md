# AgentForge 统一运行观测方案

## 目标

这套方案服务于所有小 A 和大 A，回答两类问题：

1. Agent 内部的数据如何流转：输入、子 Agent、模型、工具、判断、证据和产出物之间的关系。
2. Agent 对外消耗了什么：模型、Token、工具次数、耗时、错误和可发布产出。

方案不输出模型隐藏的逐步推理链，而是记录公开可审计的工作摘要、判断依据、证据引用、置信度和待确认项。

## 总体结构

```text
请求 / MCP
  -> 鉴权与 RunContext
  -> Agent Runtime（大 A / 小 A）
  -> LLM / 工具 / 子 Agent / 文件产出
  -> 统一运行事件
  -> 校验、脱敏、父子关系和可见性处理
  -> 内部运行账本 + Token 账本
  -> ExternalViewBuilder
  -> MCP / API 对外发布
```

大 A 和小 A 通过 `run_id`、`parent_run_id`、`event_id` 和 `sequence` 关联。每一次模型调用、工具调用、决策、证据绑定、产出物生成和错误都必须有统一事件。

## 内存优先的冷热分层

不把完整历史长期保存在 AgentForge 进程内，也不把每一次查询都落成本地文件。采用 Redis/内存热层加外部持久层：

| 数据 | 热层 | 冷层 | 默认保留 |
|---|---|---|---|
| 当前运行上下文 | Redis + 进程短引用 | 运行结束摘要 | 运行期间和最近 24 小时 |
| 运行事件、决策摘要、证据引用 | Redis | 外部持久化账本 | 最近 7 天 |
| Token、耗时、错误指标 | Redis 聚合计数 | Prometheus/OTel 后端 | 最近 30 天 |
| 完整模型正文、工具原文 | 仅当前任务和短期缓存 | 对象存储或项目产出物 | 按项目策略 |
| 大型 Markdown、附件和文件 | 不进入常驻事件内存 | 项目工作空间/对象存储 | 按项目生命周期 |

事件中保存引用、摘要和内容哈希；只有当前运行需要的正文进入热缓存。对外查询优先从热层返回，热层缺失时按权限从冷层补读。

## 信息完整性

- 所有 HTTP、MCP、Agent、LLM、工具和产出物入口统一发事件。
- 事件至少包含 `event_id`、`run_id`、`parent_run_id`、`sequence`、时间、操作者和事件类型。
- 运行账本是业务事实来源；OpenTelemetry 是可采样、可异步失败的观测副本。
- 写入结束事件前校验父子关系、序号连续性和必填字段。
- 运行异常时生成 `run.failed` 或 `run.incomplete`，不能静默丢失。
- 事件提交和对外发布解耦，外部接口只能读取已通过策略校验的 `ExternalView`。

## 信息安全

每个字段带有可见性：`internal`、`owner`、`team`、`external`、`redacted`、`forbidden`。API Key、密码、Redis Key、服务器绝对路径、其他账号数据和未脱敏隐私内容禁止进入对外视图。

脱敏发生在 OTel 导出和对外发布之前。Trace 属性只记录 ID、类型、长度、哈希和摘要，不记录完整提示词、完整用户正文或凭证内容。

## 内存估算

以下估算以 AgentForge 服务、Redis 热层和观测组件合计计算，实际值取决于模型并发、上下文长度和工具返回大小：

| 档位 | 适用情况 | 建议总内存 | 说明 |
|---|---|---:|---|
| 最低可用 | 1-3 个并发运行，热数据 24 小时，正文短引用 | 24 GiB | 可以运行，但没有太多峰值余量 |
| 推荐 | 5-15 个并发运行，热数据 7 天，保留摘要和证据引用 | 32 GiB | 适合当前多账号小 A 使用和后续大 A 试运行 |
| 较高并发 | 15-40 个并发运行，较长上下文和多工具调用 | 48-64 GiB | 适合正式生产和多个大 A 并行 |

推荐把机器扩到 **32 GiB**。如果预计多个账号同时运行长论文、专利和大 A，并且希望保留较多热数据，直接扩到 **48 GiB 或 64 GiB**。当前 15 GiB 且可用内存约 1.2 GiB，不适合直接启用长期事件保留和观测组件。

粗略预算如下：

```text
AgentForge Python 服务       0.8 - 1.8 GiB
Redis 热事件与会话           1.0 - 4.0 GiB
OTel Collector/Jaeger/指标   0.5 - 2.5 GiB
模型并发与上下文峰值          2.0 - 8.0 GiB
系统和突发余量               4.0 - 8.0 GiB
```

热层设置硬上限，按账号、项目和运行数量限制事件正文缓存；达到上限时先淘汰完整正文，保留事件元数据、摘要、证据引用和 Token 统计，不能让观测数据挤占聊天服务内存。

## 实施和验收顺序

1. 先补统一事件模型、父子运行关系、Token 账本和字段级可见性测试。
2. 覆盖 HTTP、MCP、大小 A、模型、工具、文件产出、错误和取消等所有节点。
3. 在本地启用内存热层和 OTel 测试导出器，验证事件顺序、脱敏、限额和故障降级。
4. 测试全部通过后，由用户验收运行链路、内部视图和对外视图。
5. 用户验收通过后才部署线上；未验收前不启用线上数据结构变更。

## 设计约束

- 不把隐藏思维链作为业务接口或持久化契约。
- 不把 OpenTelemetry 当作唯一业务账本。
- 不在 AgentForge 进程内无限积累事件和完整正文。
- 不在用户验收前推送线上。
